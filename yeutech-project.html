🏗️ Clean Architecture & Domain-Driven Design

To ensure the application remains maintainable and scalable as business logic grows, the backend was strictly engineered using Clean Architecture and Domain-Driven Design (DDD) patterns. This decouples the core business rules from frameworks and databases.

Presentation / Web Layer (Controllers, DTOs, Security Filters)
↓ ↑
Application Layer (Use Cases, Application Services, Interfaces)
↓ ↑
Domain Layer (Entities, Value Objects, Domain Events, Domain Rules)
↑ ↓
Infrastructure Layer (MySQL, JPA, Redis, SMTP, External APIs)

Core Architectural Decisions

  • Dependency Rule: Source code dependencies only point inwards. The core Domain Layer has zero dependencies on Spring Boot or MySQL, making it purely testable with standard Java unit tests.
  • Bounded Contexts: The application is split into logical modules (e.g., IdentityAccess, MarketingCampaigns, Billing) to prevent monolithic entanglement.
  • Ports and Adapters: The Application layer defines interfaces (Ports) such as UserRepository. The Infrastructure layer implements these (Adapters) using Spring Data JPA, allowing us to swap databases without touching business logic.

🛡️ Advanced Spring Security Architecture

The platform implements a highly customized, stateless security architecture leveraging Spring Security 6.x (Spring Boot 3) to protect all API endpoints and manage user identity securely.

1. Bean-Based Security Filter Chain

Moving away from deprecated configuration adapters, the security rules are defined via a modernized SecurityFilterChain bean. This explicitly disables CSRF (as we use stateless JWTs) while strictly configuring CORS to only accept requests from allowed React frontend origins. It defines public ingress routes (e.g., /api/v1/auth/**) and secures all others by default.

2. JWT Authentication Filter

A custom JwtAuthenticationFilter (extending OncePerRequestFilter) intercepts every incoming HTTP request. It extracts the JWT from the Authorization: Bearer header, verifies the RSA cryptographic signature (preventing tampering), and checks expiration. If valid, it constructs a UsernamePasswordAuthenticationToken and securely injects it into the SecurityContextHolder for the request lifecycle.

3. UserDetailsService & BCrypt

Authentication relies on a custom UserDetailsService that queries the MySQL database. Passwords are never stored or compared in plain text. Instead, we use the robust BCryptPasswordEncoder with a high work-factor algorithm, effectively mitigating brute-force and rainbow table attacks.

4. Security Exception Handling

To ensure the React frontend always receives predictable JSON responses rather than standard Spring HTML error pages, we implemented custom AuthenticationEntryPoint (for 401 Unauthorized errors) and AccessDeniedHandler (for 403 Forbidden errors). These handlers seamlessly integrate with our global RFC 7807 ProblemDetail JSON structure.

5. Email Verification & OTP Recovery

  • Registration Flow: Users are created with a PENDING state. The system publishes a UserRegisteredEvent, asynchronously generating a secure, time-limited cryptographic token emailed to the user for activation.
  • OTP-Based Password Recovery: Instead of generic reset links, a secure 6-digit One-Time Password (OTP) is generated using SecureRandom, hashed, and stored in the database with a strict 10-minute Time-To-Live (TTL).

⚡ RESTful API Ecosystem & Role-Based Access Control

The backend exposes 20+ robust RESTful endpoints with deep Spring Security integration for fine-grained authorization.

API Design & Exception Handling

  • Standardization: Adheres to Level 2 of the Richardson Maturity Model, using resource-based URLs.
  • Global Exceptions: Uses Spring's @RestControllerAdvice to intercept exceptions globally.
  • Pagination & Sorting: All collection-returning endpoints implement Spring Data's Pageable.

Method-Level Security (RBAC)

Security goes beyond basic URL matching. By enabling @EnableMethodSecurity, we implemented fine-grained, method-level authorization directly on our service and controller layers.

  • Role Verification: Endpoints are guarded with annotations like @PreAuthorize("hasRole('ADMIN')"). Roles (e.g., ROLE_USER, ROLE_MANAGER) are extracted directly from the verified JWT claims so the database doesn't need to be queried on every request.
  • Custom Permission Evaluators: For complex business rules, we use SpEL (Spring Expression Language) to enforce ownership. For example, @PreAuthorize("@securityService.isOwner(authentication, #userId)") ensures a user can only modify their own profile data unless they possess superior admin privileges.

🗄️ Database Schema Evolution & Persistence

Data integrity is paramount. We selected MySQL for its robust relational guarantees, and Flyway to manage the schema lifecycle deterministically.

Migration Strategy with Flyway

  • Version Control for DB: Every database change (DDL/DML) is stored in versioned SQL scripts (e.g., V1__init_schema.sql, V2__add_otp_table.sql) committed to Git.
  • Environment Consistency: When the Spring Boot application starts, Flyway automatically checks its metadata table and applies pending migrations sequentially. This guarantees that Dev, Staging, and Production environments have perfectly synchronized schemas without manual DBA intervention.

💻 Frontend Client Integration

The client application is built with React and TypeScript, communicating securely with the backend API.

Technical Implementations

  • End-to-End Type Safety: Backend DTOs (Data Transfer Objects) are mirrored as TypeScript interfaces on the frontend. This prevents runtime errors related to missing or malformed data properties.
  • Axios Interceptors: API calls are managed via Axios. We implemented request interceptors to automatically attach the JWT Authorization: Bearer header. Response interceptors are used to seamlessly handle 401 Unauthorized errors by attempting a silent token refresh in the background before retrying the failed request.

🐳 Containerization & DevOps

To achieve reliable, repeatable deployments, the entire stack was containerized using Docker.

Deployment Architecture

  • Multi-stage Dockerfiles: The backend uses a multi-stage Dockerfile. Stage 1 compiles the Java 21 code using Maven/Gradle. Stage 2 copies only the compiled .jar into a lightweight JRE base image (e.g., Alpine or Distroless), keeping the final image tiny and secure.
  • Environment-Based Configuration: The Docker containers are stateless. Variables like database credentials, JWT secret keys, and SMTP server details are passed as environment variables at runtime, overriding Spring's application.yml.
  • Secure API Routing: The Docker network isolates the database from the public internet. An API Gateway/Reverse Proxy (like Nginx) sits at the edge, terminating SSL/TLS, serving the React static files, and securely proxying /api/* requests directly to the Spring Boot container.
